# KnifeCraft — Phase 2 plan: customers and the order lifecycle (2026-10-30)

Scope: **planning only.** No code changed. Read from `main` = `f75acf2` (Phase 1 done, not pushed). Builds on what
exists; nothing here adds a second engine, wallet, ledger, event bus or top-level save field.

## 0. What exists today (verified in source)

| Piece | Where | State |
|---|---|---|
| Order state machine `PENDING→ACTIVE→PREPARING→READY→SERVED→PAID→COMPLETED` | `service/orderStateTypes.ts`, `CustomerOrderManager.ts` | One linear chain; pay only on `SERVED→PAID` |
| Pay once, cash kept with the order | `economy/pendingCash.ts` | Done |
| Customers after a level's own orders | `restaurant/menuGuests.ts` `customerQueue` | Menu guests (`menuGuestsFor`: schedule + seats, capped by team capacity) then one walk-in, **one at a time**, after the level's orders |
| Dish choice for guests | `menuGuestQueue` → `OrderGenerator.generateOrder` (seeded, recent-dish penalty) | From the **active menu** (unlocked + switched on). **Stock is not considered**, except the walk-in (`walkInStock`, which keeps the next level's stock aside) |
| Floor: 2 seats, parties of 1–4, walk in / eat / leave | `restaurant/serviceFloor.ts`, `ServiceFloor.tsx` | Customers come one party at a time, when the previous one is done |
| Arrival clock, queue, patience | — | **Not built** |

So Phase 2 is three things: **a clock** (when customers arrive), **a queue** (who is waiting, how long they wait), and
**a stock-aware dish pick**. The order chain itself barely changes.

## 1. Order state machine: no COOKING state

**Recommendation: keep the 7 order states; do not add COOKING.**

- Cooking is already a step *inside* PREPARING (the cooking film or oven tray after the cut). Making it a state would
  change the chain every order uses, with no rule hanging on it: pay, stock and score happen at READY / SERVED / PAID.
- What Phase 2 needs is a **customer** lifecycle, which is a different thing from the order's. It gets its own small
  machine, kept in memory on the floor (never in the save):

```ts
// restaurant/serviceFlow.ts (new, pure)
export type GuestState =
  | "ARRIVING"  // walking in from the door
  | "WAITING"   // in the queue at the door; patience drains
  | "SEATED"    // at a table; the order is PENDING..READY (patience paused)
  | "EATING"    // served, paid (cash on the table)
  | "LEFT"      // walked out happy
  | "WALKED_OUT"; // patience ran out while WAITING: no order, no pay, no penalty
```

Order states stay the source of truth for money; `GuestState` only drives the floor and the queue.

## 2. Arrival scheduler

**Where:** `restaurant/serviceFlow.ts`, pure and seeded. The schedule is computed once per service from the save and
the level, so the same save always gives the same customers at the same times (testable, no `Math.random`).

```ts
export type Arrival = {
  id: string;              // "lvl-12:a3" — stable, deterministic
  atMs: number;            // service-clock time the guest reaches the door
  kind: "order" | "guest" | "walk-in"; // "order" = the level's own required ticket
  recipeId: string;
  partySize: 1 | 2 | 3 | 4;
  patienceMs: number;      // how long they wait in the queue before walking out
};

export function arrivalSchedule(save: SaveData, level: LevelDefinition): Arrival[];
export const PACE: { fromLevel: number; gapMs: number; patienceMs: number }[] = [
  { fromLevel: 1,  gapMs: Infinity, patienceMs: Infinity }, // L1–4: one at a time, as today (learning)
  { fromLevel: 5,  gapMs: 35_000,   patienceMs: 150_000 },
  { fromLevel: 20, gapMs: 28_000,   patienceMs: 120_000 },
  { fromLevel: 40, gapMs: 22_000,   patienceMs: 100_000 },
];
```

- **Order of arrivals:** the level's own required orders come first and keep their order (they teach); guests and
  the walk-in arrive between them on the gap. Counts are today's (`menuGuestsFor`, `walkInsFor`), so the number of
  paying customers per service does not change.
- **Gap shortens with the team:** `gapMs × (2 / max(2, menuGuestCapacity))`, floor 15 s, so a bigger team is fed faster.
- **The service clock** is a React hook (`useServiceClock`) that adds frame time from `requestAnimationFrame`, each
  step clamped to 250 ms. It runs only while a service is on screen and no card is open.
  - **App backgrounded:** the browser stops animation frames, so the clock stops. No Page Visibility API (banned by
    preflight), no catch-up burst on return.
  - **App closed:** nothing happens while closed. On reload the service is rebuilt from the save (`paidOrders`,
    `menuGuests`, as today); the clock restarts at 0, so the next unserved customers arrive again. Nobody is lost or
    paid twice. **No offline arrivals** (offline income is Phase 5 / D5).
  - **Paused** during a story card, the Pre-Service Check, a teaching first play and any modal.

## 3. The multi-customer queue

```ts
export type QueueState = {
  clockMs: number;
  guests: { arrival: Arrival; state: GuestState; waitedMs: number }[];
};
export const QUEUE_MAX = 4; // people waiting at the door; more arrivals wait outside (not shown)

export function stepQueue(q: QueueState, dtMs: number, seatsFree: number): QueueState; // pure reducer
export function nextToSeat(q: QueueState): Arrival | null; // FIFO; a required "order" never walks out
```

- **Size:** up to 4 waiting at the door, 2 tables (today's `FLOOR_SEATS`). A party takes one table.
- **Who goes next:** first come, first served. A level's required order never walks out (patience ∞), so a level can
  always be finished.
- **Patience:** drains only while WAITING; paused once seated. When it runs out the guest **walks out**: no order, no
  pay, no ledger entry, no penalty beyond the lost sale (decision Q3).
- **UI on the floor:**
  - a door strip of up to 4 small faces with a patience ring each, plus "🚪 3 waiting";
  - while cutting, a HUD chip "🚪 2 waiting ⏳";
  - a guest who walks out shows a short 😤 and leaves by the door (the existing leave walk);
  - Next Customer seats the queue head (today's button, now fed by the queue).
  Text stays short; the rule sits behind an ⓘ (`ui-copy-qa`).

## 4. Orders from what is unlocked AND in stock

```ts
// restaurant/orderPool.ts (new, pure)
export type PoolEntry = { recipe: RecipeDefinition; weight: number; why: "stocked" | "no-stock-rule" };
export function orderPool(save: SaveData, level: LevelDefinition): PoolEntry[];
```

- **Pool** = active menu (unlocked + switched on, `activeMenuRecipes`) ∩ cookable (specialist cuisines only with
  their chef, the `cookableMenuDishes` rule) ∩ **in stock**.
- **In stock** = the dish's ingredients are usable **after** setting aside what the level's remaining required
  orders and the next level's orders need (the `walkInStock` reserve rule, applied to every guest). Before stock is
  used (`serviceUsesStock`, Level 15), every menu dish counts as in stock.
- **Weight** (then the existing recent-dish/cuisine penalties in `generateOrder`, which gets an optional weight):
  - 1.0 base;
  - ×1.5 for a dish new on the menu in the last 5 services (players see what they unlocked);
  - ×(0.5…1.5) by how many full portions are in stock (`min(portions, 3) / 2`), so plenty of stock sells first and
    the last portion is ordered less;
  - the menu price never changes the pick (no money weighting).
- **Stock runs out:** a dish leaves the pool the moment it can't be made beside the reserve. When the pool is empty,
  guests stop arriving (the walk-in and remaining guests are skipped, as the walk-in is today). The door shows
  "🥕 Out of stock · Market" (one line, ⓘ explains). Required level orders are unaffected: they are already gated by
  the Pre-Service Check.
- **Dish chosen at arrival time, not at schedule time,** so stock bought or used during the service is taken into
  account. Still deterministic: the pick uses the seeded generator keyed by the arrival id.

## 5. How it fits with the rest

| System | Behaviour |
|---|---|
| Levels | Still the hidden schedule: a level = one service. It completes when its required orders are served (unchanged). Guests still waiting when it completes **carry over** to the next service when the service rolls on. |
| Roll-on / story cards | A story card pauses the clock. Going back to the Kitchen (P3) lets waiting guests leave quietly (no penalty, nothing saved). |
| Prep Cook | Unchanged rule (from Level 20, hired). His cutting time counts on the service clock, so with him the queue moves faster. |
| Auto service | Seats the queue head, cuts, serves, collects and repeats. It stops (as now) at the Pre-Service Check, a story card and hand-swiped cash. With Auto on, patience pauses (nobody walks out while Auto runs; decision Q4). |
| Teaching first plays, Levels 1–4 | One customer at a time, no clock, no patience (as today). |
| Interstitial ads | Unchanged: only at natural breaks (closing time, level boundaries). Never while a queue is waiting. |
| Endless Restaurant | Unchanged in this phase (it has its own day demand). |

## 10. Core sketch

```ts
// serviceFlow.ts — the reducer the floor runs every frame (pure)
export function stepQueue(q: QueueState, dtMs: number, seatsFree: number): QueueState {
  const clockMs = q.clockMs + Math.min(dtMs, 250);
  const guests = q.guests.map((g) => {
    if (g.state !== "WAITING") return g;
    const waitedMs = g.waitedMs + Math.min(dtMs, 250);
    return waitedMs >= g.arrival.patienceMs ? { ...g, state: "WALKED_OUT" as const, waitedMs } : { ...g, waitedMs };
  });
  // Arrivals due by now join the queue (beyond QUEUE_MAX they wait outside: added later, in order).
  const waiting = guests.filter((g) => g.state === "WAITING").length;
  const due = pendingArrivals(q, clockMs).slice(0, Math.max(0, QUEUE_MAX - waiting));
  return { clockMs, guests: [...guests, ...due.map((a) => ({ arrival: a, state: "WAITING" as const, waitedMs: 0 }))] };
}

// orderPool.ts — what a guest may order right now
export function orderPool(save: SaveData, level: LevelDefinition): PoolEntry[] {
  const n = levelNumber(level.id);
  const reserve = [...ticketsFor(save.levelProgress, level).tickets, ...reservedTicketsFor(save, level)];
  return cookable(activeMenuRecipes(save.business.menuActivation, n), save)
    .filter((r) => !serviceUsesStock(n) || serviceStockCheck(save, n, [r, ...reserve]).ready)
    .map((recipe) => ({ recipe, weight: dishWeight(save, recipe, n), why: serviceUsesStock(n) ? "stocked" : "no-stock-rule" }));
}
```
